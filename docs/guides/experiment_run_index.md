# Experiment Run Index

Every experiment that has been generated, what it varies, and the one command that
regenerates it. A **run** here is one *tree*: the directory of YAML configs under
`experiments/<slug>/`, the matching sbatch scripts under `jobs/<slug>/`, and the
results the jobs write to `results/<slug>/`. All three share the slug, and the slug
is a pure function of the corpus and the suite — see [Naming](#naming).

All but the last section are emitted by `scripts/gen_simplex3.py`, the config
generator. Nothing in a generated tree is hand-edited: every file carries a
`GENERATED BY scripts/gen_simplex3.py -- do not edit by hand.` header, and the
regression test is that every tree below regenerates byte-for-byte
([Regenerating](#regenerating-and-the-byte-identity-check)).

Related: [Experiment Suites](experiment_suites.md) for what a `Suite` is and which
fields it carries, [Terminology](../terminology.md) for *vertex axis*, *grid
denominator*, *qmix* and `nsamples_train`.

## Naming

```
experiments/simplex3[<corpus suffix>][<qmix suffix>][<suite suffix>][_data]/
jobs/       ↑ same slug ↑
results/    ↑ same slug ↑
```

- The corpus suffix comes from `DataSimplexSpec.suffix` (`""` for yahoo, `_dolly`,
  `_oasst1`, `_pool`, `_nsweep`).
- The suite suffix comes from `Suite.tag` (`""` for the original llama suite,
  `_qwen`, `_olmo2`, `_rsweep_olmo2`, …).
- Dataset-first ordering is deliberate: `simplex3` stays `simplex3`, and a second
  corpus on the same model reads as `simplex3_dolly_qwen` rather than as a variant
  of the qwen suite.

The `--suite` and `--dataset` values are *not* the slug. `--suite olmo2_nsweep
--dataset yahoo_nsweep` writes `simplex3_nsweep_olmo2_nsweep`, because the tag and
the suffix are both spelled out.

Every run also owns a **job prefix**, the short token every SLURM job name in the
tree starts with. It is written down rather than derived, because it lands in
`sacct` history and log filenames and is permanent once submitted.

## The base runs — one corpus, one base model

The yahoo 2-simplex: ten topics partitioned into three semantic groups, mixtures at
every 25% of those groups, 16 adapters (15 grid points plus the even mixture).

| Run | Base model | Adapters | Job prefix | Generate with |
|---|---|---|---|---|
| `simplex3` | `meta-llama/Llama-3.1-8B` | 16 | `s3` | `python scripts/gen_simplex3.py` |
| `simplex3_qwen` | `Qwen/Qwen3.5-4B` | 16 | `s3q` | `python scripts/gen_simplex3.py --suite qwen` |
| `simplex3_llama3i` | `meta-llama/Llama-3.1-8B-Instruct` | 16 | `s3li` | `python scripts/gen_simplex3.py --suite llama3i` |
| `simplex3_nemo` | `mistralai/Mistral-Nemo-Instruct-2407` | 16 | `s3nm` | `python scripts/gen_simplex3.py --suite nemo` |
| `simplex3_olmo2` | `allenai/OLMo-2-0425-1B-Instruct` | 16 | `s3o2` | `python scripts/gen_simplex3.py --suite olmo2` |

`simplex3` is the original run and the only one on a raw (non-instruct) base; it is
also the only one that probes two query sets (`full_context` and `question_only`)
and the only one that emits the dataset build and embedding jobs inline, because it
ran before those became a corpus-owned tree. The other four are chat suites at
parity with each other: `question_only` only, plus the log-probability level,
generation-mode activations and a 10-point temperature sweep.

Together the last four are a scale ladder — 1B / 4B / 8B / 12B — as well as a family
comparison, and `llama3i` against `simplex3` isolates base vs instruct at fixed
family.

so 35 grid points and 35 adapters, and neither emits dataset-level jobs — the
corpus's own `_data` tree owns those.

| `simplex3_dolly_llama3i` | dolly | Llama-3.1-8B-Instruct | `s3dli` | `python scripts/gen_simplex3.py --dataset dolly --suite llama3i` |

| `simplex3_dolly_olmo2` | dolly | OLMo-2-1B-Instruct | `s3do2` | `python scripts/gen_simplex3.py --dataset dolly --suite olmo2` |
| `simplex3_oasst1_qwen` | oasst1 | Qwen3.5-4B | `s3oq` | `python scripts/gen_simplex3.py --dataset oasst1 --suite qwen` |
| `simplex3_oasst1_llama3i` | oasst1 | Llama-3.1-8B-Instruct | `s3oli` | `python scripts/gen_simplex3.py --dataset oasst1 --suite llama3i` |
| `simplex3_oasst1_nemo` | oasst1 | Mistral-Nemo-Instruct | `s3onm` | `python scripts/gen_simplex3.py --dataset oasst1 --suite nemo` |

- **dolly** (`databricks/databricks-dolly-15k`) partitions eight instruction
  categories into four groups. `n=1000` per adapter, as yahoo.
- **oasst1** is the best-reply pairs built by `scripts/build_oasst1_pairs.py`, four
  language vertices (en / es / ru / zh). `n=500` rather than 1000, because only
  three of the four vertices clear a 1000-row pool.

Neither corpus runs a temperature sweep: greedy plus R=16 at T=1.0 is the whole
behavioral level for them.

A cross that has no entry in `_SUITE_PREFIXES` is refused rather than given a
derived prefix, because a prefix collision is only visible in `sacct` after the
fact. Adding a cross means adding that pair to the table in
`scripts/gen_simplex3.py`.

## The sweep runs — one extra axis crossed with the simplex

Each of these holds the 16-point yahoo simplex fixed and varies one further knob.
All four are OLMo-2-1B, because the axis is priced per adapter and only the 1B makes
hundreds of adapters affordable.

| Run | Axis | Adapters | Job prefix | Generate with |
|---|---|---|---|---|
| `simplex3_pool_olmo2_pool` | mixture **resolution/count** — 1000 sampled mixtures on the 1% grid, plus the 3 vertices and the even mixture | 1004 | `s3po2` | `python scripts/gen_simplex3.py --suite olmo2_pool --dataset yahoo_pool` |
| `simplex3_nsweep_olmo2_nsweep` | `nsamples_train` — 10 training-draw sizes × 10 draw seeds | 1600 declared, 1440 extracted | `s3no2` | `python scripts/gen_simplex3.py --suite olmo2_nsweep --dataset yahoo_nsweep` |
| `simplex3_rsweep_olmo2` | **LoRA rank** — 1 to 128 by powers of two | 128 | `s3ro2` | `python scripts/gen_simplex3.py --suite olmo2_rsweep` |
| `simplex3_initsweep_olmo2` | **LoRA init seed** — `torch.manual_seed` before PEFT draws `A`/`B`, ten values | 160 | `s3io2` | `python scripts/gen_simplex3.py --suite olmo2_initsweep` |

Three things are worth knowing before reading any of these:

- **The middle point is free.** Rank 16 and init seed 0 resolve to the very adapter
  directories `simplex3_olmo2` already trained — rank and init seed are both in the
  adapter name and every cache is keyed on that name — so the rsweep's new work is
  112 adapters and the initsweep's is 144, not 128 and 160.
- **The init seed is not the draw seed.** The init seed is the `_i00` token in an
  adapter directory name; the draw seed is the `s00` in `_n1000_s00` and it chooses
  which *rows* are trained on. The initsweep varies the first and holds the second,
  which is why its dataset level is an exact null control: ten identical scores, and
  a difference there is a determinism bug rather than a finding.
- **`nsamples_train` is not `n_samples_sweep`.** The first is the size of the
  training draw (the sweep's axis); the second is the size of the *embedding* draw
  the dataset level reads. The nsweep's `train_sizes` tuple is deliberately
  unsorted — shard indices are positional, and sorting it would silently renumber
  shards that have already been submitted.
- Each of these drops the log-probability level, generation-mode activations and the
  temperature sweep. None of the standing perspectives reads them and all three are
  priced per adapter.

## The probe runs — vary the query set, train nothing

| Run | Axis | Generate with |
|---|---|---|
| `simplex3_qmix_olmo2` | **qmix** — what the 100-row probe is *made of*: 0/1/2/5/10/20/50% yahoo against a dolly or an oasst1-zh diluent, ×10 seeds, plus the shared undiluted 100% point | `python scripts/gen_simplex3.py --qmix --suite olmo2` |

`--qmix` reuses the existing `_n1000_s00_r16_i00_b5008` fleet and emits no training
jobs at all — 450 configs across the behavioral, functional and greedy families, and
one `submit_all.sh`. It is defined over the yahoo fleet only; the diluents are arms
of `QMixSpec` in `src/experiments/query_mixture_spec.py`, not `--dataset`, and
passing another `--dataset` is refused with that message.

The qmix slug is `simplex3` + corpus + `_qmix` + suite, which keeps the tree off
`simplex3_olmo2` — whose adapters it reuses and whose results directory it must not
write an `experiment.yaml` into.

> **Not on `main` yet:** `qbig`, the probe-*depth* axis (the same fleet at 1000
> queries and R=64, `--suite olmo2_qbig --dataset yahoo_qbig` →
> `simplex3_qbig_olmo2_qbig`), lives on branch `worktree-qbig-olmo2-1000q-r64`. It
> belongs in the table above once that branch merges.

## The dataset trees — model-free, one per corpus

A corpus's draws and its dataset-level embeddings do not depend on any base model,
so they are built once, detached from every suite, and reused by every model tree
over that corpus. That is why none of the crosses above emits a build or embed job.

| Run | Corpus | Generate with |
|---|---|---|
| `simplex3_dolly_data` | dolly | `python scripts/gen_simplex3.py --dataset dolly --data-tree` |
| `simplex3_oasst1_data` | oasst1 | `python scripts/gen_simplex3.py --dataset oasst1 --data-tree` |
| `simplex3_pool_data` | the 1004-mixture pool | `python scripts/gen_simplex3.py --dataset yahoo_pool --data-tree` |
| `simplex3_nsweep_data` | the nsweep grid | `python scripts/gen_simplex3.py --dataset yahoo_nsweep --data-tree` |

Each emits one `01_build.sh`, one `02_embed_matrix.sh` and one `02_embed_sNN.sh` per
sweep seed. There is no `simplex3_data`: yahoo's build and embedding jobs are inside
`jobs/simplex3/`, emitted by the llama suite before the standalone tree existed.

The cache they write to is shared *between* suites on purpose
(`results/shared_cache`), which is what makes a second base model over the same
corpus cheap.

## Inspecting a run without generating it

```bash
python scripts/gen_simplex3.py --dataset dolly --list
```

prints every proportion, its group weights, and the draw and adapter totals, and
writes nothing. It resolves the corpus only, so it works for any `--dataset`
regardless of which suites that corpus has prefixes for.

Four flags override a suite in place, for a one-off variant that is not worth
registering: `--base-model`, `--tag`, `--torch-dtype`, `--target-modules`. `--tag`
is the one that changes the slug, so it is also the way to keep a variant from
landing on top of the run it was derived from. `--root` writes the tree somewhere
other than the repository.

## Submitting a run

```bash
bash jobs/<slug>/submit_all.sh
```

submits the whole chain with `afterok` dependencies. Read the header first: every
wall and partition ordering in a tree was chosen against a snapshot of free capacity
that is stale by the time it runs, and everything downstream is `afterok` on the
prefetch and build jobs.

**OLMo-2 training must not land on an l40s.** On a 48 GB card `device_map="auto"`
places part of the model off-device and the offloaded submodule hands back a meta
gradient — `RuntimeError: Function MmBackward0 returned an invalid gradient at index
1 - expected device meta but got cuda:0`, which is not a clean OOM and does not look
like one in the log. Nemo is affected the same way. The `rsweep` and `initsweep`
suites pin `train_partitions="h200,h100"` because their training runs from
`submit_all.sh`; for the other OLMo-2 and Nemo trees, training is hand-submitted
with `sbatch --partition=h200,h100`. Extraction is unaffected — it is forward-only —
and keeps the full partition list.

## Regenerating, and the byte-identity check

Every tree already on disk must regenerate byte-for-byte after any change to the
generator, to `Suite`, or to `DataSimplexSpec`. That is the whole reason the
generator exists rather than hand-written YAML, and it is stated in the docstring
but not automated.

The baseline is not all in git: `jobs/` is gitignored wholesale, and the older
experiment trees live only in the main checkout's **untracked**
`experiments/archive/`. So the check is two halves — regenerate every tree in this
file, then:

```bash
git status --porcelain -- jobs                    # clean → every sbatch file is unchanged
diff -rq experiments/archive/<tree> experiments/<tree>   # per archived tree
```

Delete the regenerated legacy trees afterwards; they are untracked scratch that will
otherwise clutter `git status`.

**Two emitted prose figures are knowingly wrong and must stay hardcoded.** Both are
in the behavioral and greedy config headers: `"~25,600 generations"` and `"all 16
adapters"` are true of the 16-adapter yahoo tree and wrong for the 35-adapter
corpora and the 1004-adapter pool. Deriving them is correct, and it rewrites ~150
config files belonging to runs that have already happened, so it belongs in a commit
whose entire subject is that prose fix. A "cleanup" that derives them will look like
a no-op and will break the byte-identity check for six trees.

One genuine pre-existing discrepancy is not a regression:
`experiments/archive/simplex3_pool_data/embed_mean.yaml` exists but the generator
has never emitted it.
